# Native CodexDeck backend

Tauri 2 account monitoring backend for the shared interface in `../docs/architecture.md`. The frontend is maintained separately in `../src`.

## Build and data

The macOS bundle declares macOS 13.0 or later, matching the existing native baseline. Windows and Linux runtime support remains unverified.

Install a current stable Rust toolchain, platform Tauri prerequisites, Node.js, and the frontend's npm dependencies. From the repository root:

```sh
npm run tauri -- dev
npm run tauri -- build --no-bundle
cargo test --locked --manifest-path src-tauri/Cargo.toml
```

`Cargo.lock` is checked in for reproducible dependency resolution. Use a current stable Rust toolchain; the package declares Rust 1.90 as its minimum. Install formatting support with `rustup component add rustfmt`.

The identifier `com.codexdeck.desktop` selects a new OS app-data directory. It never reads the Swift app's `Codex Usage` storage. Versioned `state.json` contains account metadata, typed quota snapshots, settings, resolved workspace IDs and alert transition state. Login IDs and URLs remain only in memory. The API's `workspaceId` is the requested restriction; the internal `resolvedWorkspaces` map preserves the verified routing identity independently for duplicate detection. Snapshots preserve all quota buckets and reset-credit details.

Metadata uses a synced same-directory temporary file and replacement; direct symlinks/reparse points at app root, profile root, account home and metadata are rejected. Unix account directories are created with 0700 and metadata files with 0600. Windows uses the user's app-data directory and inherited OS ACLs; explicit ACL hardening and adversarial reparse-point/ancestor-race testing remain unverified. This is not a credential export format. An unreadable, corrupt or unknown-version state is preserved and blocks all mutations until repaired, rather than being overwritten by an empty state.

For **debug builds only**, `CODEXDECK_DATA_DIR=/absolute/temporary/path` selects a synthetic test data root. The path must be absolute. Release binaries ignore this variable. Do not point it at real Swift or Codex account storage. An exclusive OS lock on the canonical data root is acquired **before metadata load**, held for the backend lifetime, and released by the kernel after a crash. It prevents competing executables or app identifiers from sharing a root. Official Tauri single-instance protection additionally initializes before backend setup: a second invocation focuses the existing window and exits before loading metadata or starting clients. Its identifier is app-wide, so separate debug data roots do not allow concurrent instances of the same app identity. Linux DBus/Snap/Flatpak integration still needs target-specific execution tests.

## Actual authentication and transport

Each UUID has its own `<app-data>/profiles/<uuid>` working directory and one `codex app-server --listen stdio://` process. It receives an allowlisted environment, explicitly isolated `CODEX_HOME` and `CODEX_SQLITE_HOME`, `analytics.enabled=false`, and **mandatory** `cli_auth_credentials_store="keyring"`. API keys, access-token variables, parent profile/database overrides, provider URLs and Electron data paths are not inherited. Routine login and refresh use the Codex CLI’s OS credential backend. The explicit full-account transfer feature reads/writes the same direct OS credential entries natively and stores complete credentials only inside password-encrypted JSON archives; it never exposes them to the webview. See [account transfer](../docs/account-transfer.md). There is no plaintext-file fallback. If the store is unavailable or locked, the operation fails with a safe explanation. The app-server also receives `auth_keyring_backend="direct"` so its credential backend matches the native archive adapter. Unsupported or inaccessible credential storage fails without a file fallback.

Transport implements initialize/initialized, numeric request correlation, a maximum 8 MiB JSONL packet, request deadlines (35 seconds normally; cancellation 5 seconds), ten-minute login expiry, pending-request cleanup, process-exit reporting and kill/reap on shutdown or timeout. Unsolicited tool/inference/credential requests receive method-not-found even if their IDs collide with a client request. stderr, packets and raw server errors are never logged. Only sanitized account/login/quota notifications are consumed. Critical events use a separate nonblocking reliable channel: only one correlated completion per accepted login and one exit per worker can enqueue. Quota signals are bounded and coalesced per worker; a full quota queue cannot block response parsing or erase a login completion. The backend exposes no generic process, filesystem, shell or credential IPC endpoint.

Browser sign-ins serialize across accounts. Completion must match both the account's current transport generation and login ID. Only HTTPS login URLs on the allowlisted OpenAI/ChatGPT hosts are accepted; embedded credentials, nondefault ports and unrelated hosts are rejected. Login does not automatically open the browser: the frontend invokes `open_login_url` after displaying pending state. Cancel stops the account's worker even when cancellation RPC fails. Cancelling an already completed/nonexistent login is idempotent and preserves Connected status. Removal waits for secure logout before deleting files/metadata; a failed logout preserves the record. Same email plus the same resolved workspace is a duplicate; different workspaces remain distinct.

Discovery searches PATH, common user/system executable locations, macOS Codex/ChatGPT app bundles, and Windows native npm vendor locations. Windows `.cmd` wrappers are never passed to a shell or directly executed. Native `codex.exe` can always be chosen in the file picker. A manually selected executable is trusted user input; automatic signature verification or CLI version gating is not implemented.

Protocol references used for implementation: [Codex App Server](https://learn.chatgpt.com/docs/app-server) and [Codex authentication](https://learn.chatgpt.com/docs/auth). Live authentication was not performed for development or validation.

## Window, scheduling and notifications

The tray supports show, hide, refresh and explicit quit. macOS Dock Reopen also restores the main window. Main-window close hides only after tray registration succeeds; otherwise normal close remains available. Pin persists and uses the native always-on-top API. `quit_app()` is an additional optional command for the frontend's Quit button. The native drag/drop handler is disabled so frontend HTML drag/drop remains usable on Windows.

Startup and manual refresh read complete account/quota responses. Polling defaults to three minutes; supported settings are 3, 5, 10, 30 and 60 minutes. Refreshes are serialized and account operations exclude competing login/removal work. Full reads follow quota notifications. A fifteen-second wall-clock watchdog detects long scheduling gaps/system sleep and refreshes on the next tick; native wake notification APIs are not yet integrated, and exact resume latency is not guaranteed.

Alerts are off by default and use the main bucket's 300-minute window. The pure transition state machine follows the Swift behavior: finite 0–100 usage, strictly below the chosen threshold, future or unknown reset time, no repeat until recovery or a changed known reset period. Transition state is persisted **before** enqueue; failed enqueue rolls back for retry. Persisted state suppresses repeats across restarts. Notifications deliberately omit account labels/emails on lock screens.

Native permission/readiness adapters replace Tauri's desktop plugin (whose desktop permission APIs unconditionally return Granted). macOS uses a small Objective-C UserNotifications bridge: no center access in unpackaged binaries; explicit enable requests Alert/Sound authorization only if not determined; every fresh-alert evaluation checks current settings. Granular authorization, visual-alert setting/style, notification-center setting and sound setting are classified by a pure tested function. Denied, provisional, unknown or known-disabled visual readiness prevents reservation. Sound-disabled/unknown sound remains deliverable only when visual readiness is established and has an explicit current warning. Permission notices are re-evaluated on fresh refresh and cleared when ready. Foreground presentation requests banner/list/sound.

Fresh valid quota recovery is persisted even while permission is denied; a blocked downward crossing never reserves an unseen alert. Reservation is saved under the metadata lock, that global lock is released during external delivery, and rollback only affects the matching account/threshold/reservation. Enqueue waits for the macOS `addNotificationRequest` completion callback; explicit failures roll back for retry. Callback registrations clean up on completion, timeout or future cancellation; the C callback does not unwind on a poisoned map lock.

**Windows/Linux visual-alert readiness is explicitly unverified and alert enable is rejected in this build.** Windows checks `ToastNotifier.Setting`, but even Enabled cannot establish registered installer identity or capture later asynchronous Failed events. Linux desktop-server reachability does not establish user permission, DND or sound settings. Neither is presented as Ready, and neither can consume an alert reservation. Their native enqueue code is retained for future integration; it is not advertised as strict acknowledged delivery. Per-target installed-session tests and stronger adapters/capability presentation remain gaps.

Acceptance is not proof of presentation: OS Focus/DND or routing can suppress a scheduled macOS notification. A scheduling timeout is indeterminate and a rolled-back retry can duplicate a late accepted notification; a crash after reservation but before enqueue or a rollback write failure can suppress it after restart. Exactly-once visible/audible delivery is not claimed. Failed rollback persistence is surfaced explicitly. No real notification or permission prompt was triggered by this implementation chat.

## Desktop integration and parity limits

On macOS, `desktopSwitch` and `desktopRestore` are true only when the installed official Codex/ChatGPT app validates against OpenAI’s signing identity and the current CodexDeck process has the packaged signed credential broker. `switch_desktop_account` and `restore_desktop_account` require the main window and execute the original-account workflow from the existing Swift implementation. Windows/Linux remain unavailable.

`build.rs` compiles the unchanged `DesktopSwitchTransaction`, original runtime, authorization, credential storage, broker protocol/client and account-only RPC source into a static Swift library. `native/macos/` supplies only the narrow metadata adapter, operation coordinator and sanitized callback boundary. Rust never sends tokens across that boundary or to the webview. The signed macOS packaging script embeds the same stable broker identity and validates both its signing requirement and the parent requirement. The shared broker builder accepts only the original Swift app or the Tauri app identifier; it retains certificate-based trust and rejects ad-hoc/foreign clients.

An explicit click requests fresh macOS owner authentication. The operation reads the original app’s effective credential configuration, checks workspace/login restrictions, stops owned credential writers, quits only the original default-home app (excluding independent account instances), snapshots both credential locations and saves a broker-only Keychain recovery marker. It synchronizes the outgoing login only to a matching known account, verifies the selected login again through the original app’s bundled CLI, and reopens the original app. The unchanged transaction rolls back partial storage writes, verification errors and launch failures. Interrupted recovery blocks active-original reads and further switches until restore/review completes. Existing backup migration tombstones and legacy archives retain their original semantics. The old Swift widget must be quit before this integration operates; a kernel file lock serializes new integration clients.

`desktopAccountId` is local metadata. Its usage client reads the original home without overriding that app’s validated credential storage mode; all other accounts continue to use isolated keyring-only homes. External account changes detach that reader without relabeling a card or letting subsequent profile login/removal target the original home. The local alias is excluded from account archives. Active-account login/removal and account transfer are blocked until switching away/restoring synchronizes the latest login back to its isolated home. Prior independent windows are still detected before replacing/removing any affected isolated credentials.

The rewrite currently does **not** implement Swift metadata import, general legacy account migration, update/minimum-version policy service, diagnostics collection or reporting. No original `.env`, service secrets or public service configuration was imported. Diagnostics remain absent rather than silently opting users in. The new `0.1.0` version has no compatibility mapping to the existing Swift build-16 minimum-version policy; do not connect it to that policy endpoint or advertise update parity without a separate platform/version manifest design. The companion service and deployment configuration are maintained outside the app repository.

macOS compilation and synthetic process tests establish a build/transport baseline, not real login, secure-store compatibility, distribution signing, notification, tray accessibility, pin or multi-instance runtime certification. Windows and Linux require their own CI build and installed-session execution; no three-platform runtime claim is made here.

## Explicit quota activation

`get_warmup`, `start_warmup` and `cancel_warmup` implement the dashboard’s immediate/one-shot short-message workflow. Mutation commands require the main window. Native scheduling, pre-send persistence, interrupted-run recovery, account locking and matching turn-completion notifications live in `warmup.rs`. See the desktop README for behavior and limits. Account-transfer exports exclude pending message jobs; imports retain only the destination’s existing job.

### Notification verification control

Settings now provides an explicit **Send test notification** action. `test_notification()` is restricted to the main window, requests permission only on this user action, checks native visual readiness, and returns a sound/readiness warning after OS submission. Errors are shown within Settings as well as the shared error presenter. Successful submission does not confirm visible/audible presentation; verify banners and sound in the installed macOS app, including foreground/background and Focus settings. This test never reads credentials or changes quota-alert deduplication state. Failed quota delivery is retried on refresh; a later successful delivery clears only the latest error owned by that same account. Notification text retains the existing no-account-identity policy on lock screens.

The **Use in Codex** action switches the original app account on signed macOS builds. It requires a connected account. Settings offers restoration; unsupported, unsigned or unpackaged builds explain the unavailable connection.
